## Database upgrade (migration `0002_verdict_audit.sql`) — APPLIED

Applied by hand in the Supabase SQL Editor (project `tqgpqkoonwywvuhbktge`) on 2026-09-30. The app never runs migrations itself. What it changed:

**`documents` table**
- `+ anchor_block bigint` — records which blockchain block a document's anchor landed in (populated by `register-onchain.js` on a successful anchor).

**`verifications` table (the audit trail)** — new columns so each verification row proves the verdict was chain-backed:
- `+ decided_by text` — how the verdict was decided (written as `"onchain"`).
- `+ chain_exists boolean` — what the chain said (exists true/false).
- `+ anchor_tx text` — the anchoring transaction hash, if known.
- `+ chain_timestamp bigint` — the on-chain timestamp.
- `+ error_class text` — reserved for classifying failures.
- **Updated `verifications_result_check` constraint** to allow `result IN ('authentic','not_found','altered','unverifiable')` — the old constraint rejected the new `'unverifiable'` value the app now writes.

Safe/idempotent: every column uses `add column if not exists`; the constraint is dropped-then-recreated. No data deleted. Re-running is harmless. Until it was applied, the audit-row insert silently no-op'd (`.catch`-swallowed) — verification itself never depended on it.
